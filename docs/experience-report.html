OpenShift on AWS: Service Control Policy Constraints and Bring-Up Findings

Account: 342831714456   Region: il-central-1   Platform: OpenShift 4.22, user-provisioned infrastructure

1. Purpose and scope

This document reports on the deployment of an OpenShift 4.22 cluster into this AWS account. It is written for the account owner, not for the engineering team that carried out the work.

The account's Service Control Policy blocks a substantial part of the installation path that OpenShift's standard AWS deployment relies on. The cluster is running: bootstrap completes, all master nodes are Ready, and workloads including an internal image registry are operating. That outcome was reached by replacing five AWS-managed services — DNS, load balancing, machine image import, VPC endpoints, and in-cluster credential issuance — with self-hosted substitutes running on a single administrative instance.

This document exists to make three things explicit: which specific API calls were blocked and how each was confirmed; what those blocks cost in engineering effort; and, most importantly, which parts of the resulting cluster are permanently degraded as a direct consequence, with no available workaround. Section 8 recommends the specific policy relaxations that would retire the largest amount of that cost.

3. The restrictions encountered

3.1 Route 53 (DNS)

The cluster's DNS names are served by a resolver running on the administrative instance rather than by Route 53. This substitution was carried forward from an earlier deployment attempt against the same account restrictions and was not independently re-verified in this engagement, because the current design has no code path that would call the Route 53 API in the first place.

3.2 VPC creation

Verified by direct API call. The deployment uses a VPC and subnet supplied by the client rather than creating its own.

3.3 Elastic IP allocation

Verified by direct API call. No instance in this deployment holds a public IP address. All administrative access runs through AWS Systems Manager Session Manager, which requires no inbound network path at all.

3.4 Load balancer creation

Verified by direct API call. A standard OpenShift installation provisions a Classic or Network Load Balancer in front of the API and application traffic. That call is denied outright, so load balancing is instead performed in software (HAProxy) on the administrative instance, forwarding to the master nodes directly.

3.5 Launching or copying a machine image the account does not own

Verified by direct API call. Both operations were denied against Red Hat's published base image for this platform. The workaround builds an account-owned image from scratch: a disposable helper instance streams the vendor's raw disk image onto a blank volume it controls, which is then snapshotted and registered as an image this account owns and may legally launch. This is a well-established technique for this exact situation, and it was verified working end-to-end, but it adds a build step — roughly 10–15 minutes — to every cluster bring-up that a normal installation does not require.

3.6 AWS's image-import service (vmimport)

Verified by direct API call. A real image-import task was submitted and denied with an explicit policy citation against the AWS-managed role that service uses internally — the same policy that blocks 3.5. This finding closed off a previously-used, and simpler, installation method for this platform entirely (see Section 6.1), making the custom image build in 3.5 the only viable path.

3.7 VPC endpoint creation

Verified by direct API call. The original design had cluster nodes fetch their boot configuration directly from private cloud storage through a VPC endpoint. With endpoint creation denied and no existing endpoint available to reuse, that design was replaced: the administrative instance now fetches the boot files itself, using its own permitted access, and relays them to nodes over the internal network. Functionally equivalent, but it makes the administrative instance a dependency for every node boot.

3.8 & 3.9 Issuing an AWS identity to in-cluster software

Both verified by direct API call, each returning an explicit policy denial. These two restrictions close the only two supported mechanisms — static credentials and federated/OIDC identity — by which a piece of software running inside the cluster can be given permission to call AWS APIs on its own behalf. They are treated separately in Section 4, because their consequences reach well beyond the specific calls denied.

4. The highest-impact restriction: no identity for in-cluster software

Restrictions 3.8 and 3.9, taken together, mean that nothing running inside this cluster — no pod, no controller, no operator — can be issued an AWS credential by any of the mechanisms OpenShift supports.

The one remaining option, letting a pod borrow the identity already attached to the node it runs on, was also tested and does not work here, for a reason unrelated to the account's policy: this cluster's internal pod network does not carry the traffic needed to reach the instance's own credential endpoint. This was confirmed directly — the credential endpoint answers from the node itself but not from any pod on it — and a commonly recommended adjustment for exactly this symptom was tried and made no measurable difference. There is, in short, no path left to explore here; the restriction is final as far as this platform's networking is concerned.

The result is that no software component inside this cluster can call an AWS API, under any circumstance, for any reason. This single fact is the root cause of every item in Section 5.

The same two closed mechanisms also rule out deferring human login to an AWS-side or federated identity provider — that path needs exactly the credential-issuing capability this section describes as unavailable. Section 5 records the consequence.

5. What is permanently compromised

The following are direct, verified consequences of Section 4 and are not expected to change without a policy relaxation. Each was confirmed on the running cluster rather than inferred.

AreaStatus
Cloud-native block storageUnavailable. No storage driver can be given an AWS identity, so cluster storage runs over a file-sharing protocol (NFS, backed by Elastic File System) instead. This works for general workloads but not for anything requiring block-level, single-writer storage semantics — a database being the typical case.
Storage platform health statusPermanently shows a fault condition. The storage component cannot be told to stand down cleanly on this platform; this is expected and does not indicate an active problem.
Machine lifecycle managementPermanently shows a fault condition. The controller responsible for reconciling machine records has no credential to act with.
Cluster network platform health statusPermanently shows an in-progress condition, though the network itself functions normally. One optional sub-component (cloud-specific network configuration, not used by this deployment) cannot start.
Internal image registryRunning, but backed by file storage rather than object storage, despite object storage being network-reachable from this environment — the obstacle is exclusively the identity restriction in Section 4, not connectivity. Red Hat's published guidance advises against this storage backend for the registry; a full read/write cycle has been verified working, but this configuration carries a caveat the vendor has not fully validated.
Application traffic routing (ingress)Runs directly on the master nodes' own network interfaces rather than behind a managed load balancer — a decision that is fixed at install time and cannot be changed afterward without rebuilding the cluster's networking configuration from scratch.
Single point of failureDNS, load balancing, and node boot delivery all run on one administrative instance. A managed AWS deployment would normally distribute these across redundant, AWS-operated services; here, that redundancy does not exist.
Cluster user authenticationEvery cloud-backed login method — AWS IAM, IAM Identity Center, or any external identity provider — is closed off by the same restriction as Section 4. Human logins to the cluster are instead served by a password file the cluster stores and manages itself. There is no central user directory, no single sign-on, and no shared group membership with the rest of the organization; adding, rotating, and removing individual logins is a manual, per-cluster task. Confirmed on the running cluster, not inferred.

6. Where the effort went

The items below are dead ends that were tried, confirmed not to work, and abandoned. They are recorded because each one represents verified engineering time that a less-restricted account would not have required.

6.1 An alternative, simpler installation method was ruled out

OpenShift offers a second installation method that avoids most of the work described in this document, at the cost of routing the vendor's base image through AWS's standard image-import pipeline. That pipeline was tested directly against this account and denied (Section 3.6), which eliminated the simpler method as an option before any further design work could build on it.

6.2 A documented networking fix that does not apply here

The standard remedy for a pod being unable to reach its instance's credential endpoint is a one-line network configuration change. It was applied and tested, and produced no change in behavior (Section 4). The change was reverted rather than left in place, since it widens the instance's exposure for no benefit.

6.3 A storage-delivery design that had to be discarded mid-build

The original plan for delivering node boot files depended on a private network path to cloud storage. That path turned out to require the same VPC endpoint capability blocked in Section 3.7, with no existing endpoint to fall back on. The design was reworked around the administrative instance instead.

6.4 A storage platform setting that is not honored on this account

An attempt to formally disable the unusable block-storage component was rejected by the platform itself, and left the storage system in a worse-looking state (two fault conditions instead of one) until reverted. This is the origin of the permanent fault status recorded in Section 5.

6.5 Standard diagnostic tooling proved unreliable

AWS's standard console-output diagnostic for a booting instance returned nothing at all for an instance that was demonstrably running, on more than one occasion, and cost real diagnostic time before that unreliability was recognized. The more reliable alternative (a live serial connection) required working around two undocumented quirks specific to this region: a non-standard connection address format, and an authentication window of roughly one minute between setup and use.

6.6 Bring-up reliability, before and after

Before the current configuration was reached, every cluster bring-up attempt failed to complete within the platform's own 45-minute timeout. The current configuration completes in just over four minutes.

7. Day-2 operational consequences

The restrictions in Section 3 also shape ongoing operation of the cluster, not only its initial build:

  • There is no direct network path to the cluster from outside the account. Every operational session — viewing the console, running commands against the cluster — is relayed through a port-forwarding session over Systems Manager, which must be established before each use.
  • These relayed sessions time out after a period of inactivity, and the disconnect is silent — it does not produce an error at the time it happens, only on the next command issued afterward.
  • Two operational sessions run with elevated local privileges can collide on the same network port without a clear signal as to why, if a previous session was left running.
  • Individual cluster logins are created, rotated, and revoked by hand on each cluster, rather than through a shared directory that would cover every cluster at once.
  • Any such change to who can log in briefly interrupts the login system cluster-wide while it takes effect.
  • Removing someone's login does not, by itself, immediately end a session they already have open; an additional step is required, and takes effect within roughly half a minute rather than instantly.

8. Recommendations

The relaxations below are ordered by how much of the cost documented in this report each one would retire, most valuable first. Any one of them can be granted independently of the others.

  1. Permit issuing a federated (OIDC) identity to in-cluster software. This single change would retire Section 4 in its entirety: cloud-native block storage would become available, the storage and machine-lifecycle fault conditions in Section 5 would clear, and the image registry could move to object storage without the vendor's caveat. It would also retire the local password file in the new authentication row in Section 5, letting the cluster defer human login to the organization's own identity provider instead. This is the highest-leverage change available.
  2. Permit load balancer creation. Would retire the administrative instance's role as a software load balancer and remove the install-time-only, unchangeable ingress decision described in Section 5.
  3. Permit Route 53 hosted-zone management. Would retire the self-hosted DNS component and its associated single point of failure.
  4. Permit copying vendor-owned machine images, or use of the standard image-import pipeline. Would retire the custom image-build step (Section 3.5) and, combined with the standard import pipeline, would reopen the simpler installation method ruled out in Section 6.1.

9. Appendix: how these findings were verified

Every restriction reported in Section 3 was checked against the real account, using one of two methods, and each finding above states which applies:

  • Automated capability probes — a repeatable script that attempts the specific AWS API call in question and classifies the result three ways: the call was denied (confirming the restriction), the call unexpectedly succeeded (flagging that a workaround may no longer be necessary), or the call failed for an unrelated reason (flagged for manual review rather than counted as evidence either way). This currently covers VPC creation, Elastic IP allocation, and load balancer creation.
  • Direct, one-time verification — a real API call made manually during the engagement and its response recorded. This covers the machine-image restrictions, the image-import pipeline, and both in-cluster identity restrictions; these are not yet part of the repeatable probe script.

One exception: the Route 53 restriction (Section 3.1) was carried forward from a prior engagement against this account and has not been independently re-confirmed in this one, since the current design never attempts that call. It is reported here for completeness, not as a freshly verified finding.
